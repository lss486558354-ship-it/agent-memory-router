# memory-manager

本 Skill 规定「怎么用」记忆库。硬性约束见仓库根目录的 `CLAUDE.md`，
这里只讲操作细节。

## 一、精准检索 SOP

### 第 1 步：拆关键词

不要直接把用户的长句丢进 `search_memory`。先把问题拆成 2–4 个**名词性关键词**：

| 用户问法 | 不该搜 | 该搜 |
|---|---|---|
| 「上次那个浏览器串味的问题怎么修的」 | 「上次那个浏览器串味的问题怎么修的」 | `浏览器`、`上下文`、`串味` / `context` |
| 「报价那个方案最后定了吗」 | 「报价那个方案最后定了吗」 | `报价`、`方案`、`decision` |

索引是子串匹配，不是语义检索。关键词越短越稳。

### 第 2 步：先宽后窄

```
search_memory("上下文")                      # 先看全貌
search_memory("上下文", type="decision")     # 再按类型收窄
search_memory("上下文", type="decision", limit=5)
```

- 命中 0 条 → 换同义词 / 英文词 / 更短的子串，再试一次。
- 命中过多 → 加 `type` 过滤，或换更具体的词。
- **最多试 3 轮**。仍然没有，说明这段历史从未被记录，
  如实告诉用户，不要编造。

### 第 3 步：判断是否值得读原文

摘要（title + keywords）通常足以回答「有没有这件事」。
只有下面三种情况才调 `read_raw_data`：

1. 需要知道**具体做法**或**具体原因**
2. 需要引用其中的数字、路径、命令
3. 摘要含糊，无法判断相关性（此时可以先用 `max_chars=500` 看开头）

**一次最多读 1–3 条。** 要读 4 条以上，说明检索没做好，回去重搜。

### 第 4 步：沿关系找上下文

拿到一条记录后，`read_raw_data` 的返回里带 `relations`。
如果 `supersedes` / `caused_by` 指向别的记录，且与问题相关，
再按 ID 取那一条 —— 这是唯一允许"顺着读"的场景。

## 二、写入 SOP

### 触发时机

出现以下任一情况就写，不要攒：

- 技术选型定了（含「为什么淘汰另一个」）
- 非平凡代码修改完成
- 缺陷根因查清
- 外部事实确认（某个 API 下线、某平台需要登录）

琐碎操作（改错别字、调整格式）不写。

### 摘要（title）写法

title 是**唯一会被检索到的内容**，它决定这条记忆以后能不能被找到。

| 差 | 好 |
|---|---|
| 「修复了 bug」 | 「独立浏览器上下文修复跨平台假阴性」 |
| 「改了报价代码」 | 「报价判定加严格价 + 上下文双条件，排除营销数字」 |
| 「用了 SQLite」 | 「选 SQLite 而非向量库：本地零依赖，关键词够用」 |

要求：

- 一行，不超过 40 字
- 包含**对象**和**结论**，不含「今天」「刚才」这类相对时间
- 不用代词（「它」「这个」）

### 原文（content）结构

建议四段，缺一不可：

```
背景：为什么会遇到这个问题
做法：具体改了什么 / 决定了什么
原因：为什么选这个而不是别的（含被淘汰的方案）
遗留：还有什么没做、什么情况下需要重新考虑
```

### 关键词（keywords）

写 3–6 个，覆盖三种说法：

- 领域词：`报价`、`playwright`
- 症状词：`假阴性`、`需登录`
- 英文/缩写：`context`、`OCC`

以后搜任何一个都能命中。

### 类型（type）

| type | 判断标准 |
|---|---|
| `decision` | 有取舍，存在被放弃的选项 |
| `code_change` | 改了代码，且原因不在代码里 |
| `issue` | 有「现象 → 根因 → 修复」链条 |
| `note` | 单纯的事实结论 |
| `reference` | 指向外部资料 |

### 建立关系

- 新方案取代旧方案：`relates_to="D_0003:supersedes"`
- 修复由某问题引起：`relates_to="I_0002:caused_by"`
- 实现某个决定：`relates_to="D_0001:implements"`

关系是**有向**的，方向写反了以后顺着读会走错。

## 三、反模式

| 反模式 | 后果 |
|---|---|
| 把整段对话原样存进 content | 原文库变成垃圾场，检索全是噪声 |
| title 写成「记录一下」 | 以后永远搜不到 |
| 搜不到就编一个答案 | 比"不知道"危害大得多 |
| 一次读十几条原文 | 上下文照样爆，系统白建 |
| 摘要里塞进全部细节 | 索引失去"小而精"的意义 |
| 决策改了但不写新记录 | 下次 Agent 会按旧结论行动 |

## 四、命令行对照

Agent 走 MCP；人排查问题时用 CLI，两者操作的是同一份数据：

```bash
python cli.py search 报价 --type decision
python cli.py show D_0001 --max-chars 800
python cli.py add --type issue --title "..." --content-file note.md
python cli.py link D_0005 D_0003 supersedes
python cli.py stats
```
